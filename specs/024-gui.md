# Spec 024: GUI

> **Normative.** This document defines `git-loom-gui`, the window on the integration branch: how it is built and started, and what it shows.

## Executable

`git-loom-gui` is a second executable of the package, built only with the `gui` cargo feature (Slint), from the library `git-loom` is built from. `git-loom` never runs the window itself. Slint 1.19 needs Rust 1.95: the feature does too, while `git-loom` keeps the package's `rust-version`.

```bash
git-loom-gui
```

It opens on the repository of the directory it is started in; one process shows one repository. Its arguments are ignored, the sequence editor's apart (below), and neither `--agent` nor `LOOM_AGENT` has an effect on it.

On Windows a release build is a GUI program, with no console; a debug build keeps one. The processes it starts get no console window of their own, a git command that may open an editor apart.

## CLI

```bash
git-loom gui
```

No arguments or flags. Starts the `git-loom-gui` installed in the directory of `git-loom`, or of the file `git-loom` is a link to, in the current directory and off the terminal's streams, and returns without waiting for the window to close. It needs neither git nor a repository itself: what the window cannot open on is the window's to say (see Start-up). Hidden: listed neither in `git-loom --help` nor by the completion scripts.

| Condition | Exact error |
| --- | --- |
| No `git-loom-gui` beside `git-loom` | `` `git-loom-gui` is not installed beside `git-loom`, in `<directory>`⏎`cargo install git-loom --features gui` installs both, in cargo's directory `` |
| Agent mode (Spec 019) | ``the GUI is interactive and unavailable in agent mode⏎Use `loom status` instead`` |
| The executable does not start | `` Failed to start `<path>`: <reason> `` |

## Sequence editor

The sequence editor of a rebase is the running executable (Spec 004), so `git-loom-gui` for a rebase the window starts. Called that way, it answers as `git-loom` does and opens no window.

## Start-up

| Repository state | Result |
| --- | --- |
| On an integration branch | The window, headed by the branch name |
| An operation is paused: loom's (Spec 014), or a rebase or merge of git's with no loom state | The window, headed as the TUI titles its paused view (Spec 020) |
| Anything `loom status` fails on (Spec 001), or an unreadable loom state (Spec 014) | No window: the error in a dialog with a `Close` button, and `git-loom-gui: <error>` on stderr; exit 1 |
| The dialog cannot be created either | `git-loom-gui: <error>` on stderr alone; exit 1 |

The window is titled `<directory of the working tree> — git-loom`.

## Window

A bar holding the heading, `New branch…` and `Merge a branch…`, above three panes, left to right: the local changes with their buttons under them, the board and the inspector, and a status bar under them. Light or dark as the system is; at least 882 by 480 px.

- The panes are parted by one-pixel dividers, each dragged from 3 px either side of it.
- The local changes pane is 260 px wide at first, never less, and never so wide that the board and the inspector cannot have their narrowest.
- The board has 46% of the room right of the local changes at first, between 10% and 90% as the divider between them is dragged, never less than 340 px; the inspector never less than 280 px.
- While an operation is paused, the local changes pane lists the files it leaves and the inspector takes the board's room (Paused operation).
- The window reads the repository when it opens and after each command it runs (Commands); never otherwise.

## Local changes

What `loom status` lists of the local changes, in the same order (Spec 001).

- The pane is headed `Local changes`, with `<n> file(s)`, or `no changes`. The header stands for all of them, as `zz` does.
- The list is always open: `→` and `←` on the header do nothing.
- A file is one line: its status letters, the index's in green then the working tree's in red, or `!!` for a conflict and an asterisk for an untracked file; then its path, relative to the directory the window was started in. A conflict is red and bold.
- The list scrolls when the pane is too short for it.

## Commit buttons

Under the list of the local changes, while no operation is paused: `Absorb`, `Hunks…` and `Commit…`. They are the `Absorb`, `Commit hunks…` and `Commit…` of the menu of the local changes selected (Commands), greyed out as those are, so while none is selected and while a command runs.

- Where a commit goes is the integration branch, as a loose commit, or a branch, in the order of the board; it starts where the last went: the integration branch at first, and once that branch is gone.
- Its message starts from that of the last commit confirmed, until that commit goes through: once it succeeds, or once the operation it paused is continued through, the next starts empty. It stays while that commit is paused, and once it failed, had a prompt cancelled, or was aborted. A commit cancelled before its message is confirmed leaves it as it was.

## Board

What `loom status` lists of the integration branch (Spec 001), top down in the same order.

- The **trunk** is the integration line: from a ring at its tip, named by the integration branch, to a dot at the base, named by the upstream.
- The base also reads the commit the integration branch stands on (hash and subject), and `<n> new commit(s)` when the upstream has some.
- The trunk has a dot for each commit no branch owns, beside its **card**, and one for each stack owning a commit, beside the first name of the stack.
- A branch is a **frame**: its name as a **tag**, with its remote indicator (Spec 001) drawn as a check mark, an arrow or a cross, and `<n> commit(s)` or `no commits`, then its commits as cards, newest first. A **thread** runs down the frame, from a ring at the tag through a dot at each card, in the color of the branch: one of six, by its rank among the branches.
- No line runs from a frame to the trunk.
- A **stack** is the frames of its branches joined into one, on one thread, the upper branch first. Branches at the same commit share a frame, their tags one under the other.
- A frame closes onto its tag, and opens again, by the chevron of the tag or a double click on it. Closed, it shows none of its commits; its stack keeps its dot on the trunk. Each branch of a stack closes on its own; branches at the same commit close together. A branch owning no commit has no chevron. Every frame is open when the window starts.
- A card is one line: short ID, subject, `<n> file(s)`. It opens in place onto the files of its commit, and closes again, by its chevron or a double click on that line: one line each, the status letter then the path, relative to the directory the window was started in (Spec 001). Several can be open at once, and one stays open while its branch is closed. A commit changing no file has no chevron.
- A frame is as wide as the pane leaves it, between 280 and 560 px; a card on the trunk and the names at its two ends are as wide. The board scrolls when the pane is smaller than it.
- Neither the context commits before the base nor a branch `loom status` hides are on it.

## Selection

The header and the files of the local changes, and the tags, cards, files of open cards and the base of the board can be selected, all called pieces here; the tip cannot. A selection holds one class of thing (Spec 020): the header is one, the local files another. The base is of no class: it is selected alone.

The **cursor** is the piece the selection was last put on: by a click, a `Ctrl` click that adds, or an arrow key. When it is hidden, the cursor goes to the nearest piece above it.

| Input | Effect |
| --- | --- |
| Click | Selects that piece alone; on a piece of a selection of several, once let go undragged (Drag and drop) |
| `Ctrl` click, with `Shift` or not | Adds the piece to the selection, or takes it out; a piece of another class than the selection's is left out |
| `Shift` click | Selects from the cursor to this piece, those of the cursor's class, and the cursor stays where it is; with no cursor, or from the base, it is a click |
| `↓` / `↑` | Selects alone the next / previous piece, in the order of `loom status`, from the cursor; with no cursor, the first / last; at either end, the cursor |
| `→` / `←` | Opens / closes the cursor; `←` on a file selects its commit, or the header of the local changes |
| `Esc` | Selects nothing; the cursor stays where it is |

- A click on the tip or on bare board changes nothing.
- A selected card has an accent border; any other selected piece is tinted.
- The pointer marks what it is on and a click acts on: a chevron and any piece but a card are tinted, the border of a card stands out. Nothing appears for the pointer being somewhere.
- A click on a chevron does not select. A double click selects, as its first click does.
- What is closed takes the pieces it hides out of the selection.
- After a key, the pane of the cursor scrolls as far as it takes to show it while it is selected; a piece taller than the board's pane, from its top.
- Nothing is selected when the window starts.

## Inspector

Shows one piece: the cursor while it is selected, else the first selected one in the order of `loom status`. With nothing selected it says `Select a branch, a commit or a file to see its diff.`, wrapped to its width.

| Piece | Title | Diff (Spec 020, Diff Pane) |
| --- | --- | --- |
| Header of the local changes | `Local changes` | `[local changes]` |
| Local file | `<path>`, as its line has it | Working file |
| Tag | `Branch <name>` | Branch name |
| Card | `<short ID>  <subject>` | Commit |
| File | `<path>  in <short ID of its commit>`, the path as its line on the board has it | Commit file |
| Base | `Upstream <label>` | Upstream |

Under the title, a button for each command of the selection's menu that the selection takes (Commands).

The diff is that text, a line colored for what it is (file header, index line, hunk header, added, removed, the commit line of `git show`), each tab as `loom.tuiTabWidth` spaces (Spec 020). The diff of any piece but the base is read the first time it is shown. A diff opens at its first line and column, and scrolls down to its last line and sideways to the end of its longest.

## Commands

A command runs the loom command the TUI runs on the same pieces (Spec 020), made of the selection by the same rules, but `Commit hunks…`, which hands its hunks to `loom commit -p` where the TUI's `C` stages them first: a selection a command does not take is refused alike. Its prompts are dialogs; the window opens no editor.

| Piece | Menu | Runs |
| --- | --- | --- |
| Header of the local changes | `Commit…`, `Commit hunks…` · `Fold into…`, `Fold hunks into…`, `Absorb` · `Drop all local changes` | `loom commit -l\|-b <branch> -m <message> zz`, `loom commit -l\|-b <branch> -m <message> -p --hunks <id>… --hunks-from <fingerprint>` · a drop where a click says (Drag and drop), `loom fold -p zz <commit>`, `loom absorb` · `loom drop zz` |
| Local files | `Commit…`, `Commit hunks…` · `Fold into…`, `Fold hunks into…`, `Absorb` · `Drop` | `loom commit -l\|-b <branch> -m <message> <files>`, `loom commit -l\|-b <branch> -m <message> -p --hunks <id>… --hunks-from <fingerprint>` · a drop where a click says, `loom fold -p zz <commit>`, `loom absorb <files>` · `loom drop <files>` |
| Card | `Reword…`, `Split…` · `Fold into…`, `Fold hunks into…`, `Move…`, `Uncommit` · `New branch here…` · `Drop` | `loom reword <commit> -m <message>`, `loom split -p <commit> -m <message> --hunks <id>… --hunks-from <fingerprint>` · a drop where a click says, `loom fold -p <commit> <commit>\|zz --hunks <id>… --hunks-from <fingerprint>`, a drop where a click says, `loom fold <commit> zz` · `loom branch <name> --on <commit>` · `loom drop <commit>` |
| Files of a card | `Split into its own commit…`, `Fold into…`, `Uncommit` | `loom split <commit> -m <message> <files>`, a drop where a click says, `loom fold <file> zz` |
| Tag | `Push`, `Force push`, `Take the remote version…` · `Rename…`, `New branch here…`, `Unmerge` · `Drop` | `loom push <branch>`, `loom push <branch> -f`, `loom update <branch>` · `loom reword <branch> -m <name>`, `loom branch <name> --on <branch>`, `loom unmerge <branch>` · `loom drop <branch>` |
| Base | `Update` | `loom update` |

- A right click on a piece opens the menu of its class, a line between groups (`·` above), with what the selection does not take greyed out. On a selected piece it is the selection's menu, and the piece becomes the cursor; on any other, the piece is selected alone first. A right click on nothing opens none.
- `Take the remote version…` is for a branch with an upstream. `Uncommit` takes one commit or file, and `Split into its own commit…` files of one commit, not all of them. In the bar, `New branch…` runs `loom branch` on the one commit or branch selected, else at the base, and is greyed out with more than one piece selected. `Merge a branch…` runs `loom merge --all`, whose prompt picks the branch.
- While an operation is paused only its own commands apply (Paused operation).
- One command runs at a time. Meanwhile the menus, the buttons and the bar are greyed out, a right click opens no menu, pieces can still be selected, and closing the window is refused, with a notice: it would kill the command's git mid-way. Nothing under a dialog, the log or the hunk picker starts a command either, though `Tab` reaches it.
- A prompt of the command is a dialog over the window, headed by the command line: a question (`Yes`, `Cancel`), a line to type, or a list to pick one item from (`↑`/`↓`, a double click picking and confirming) or to tick at least one of. `Enter` confirms; `Esc` cancels, and so cancels the command.
- What a `…` command needs is asked first, in a dialog of the window's own, which `Esc` closes without running anything:

  | Command | Asks |
  | --- | --- |
  | `Commit…` | The message, and where the commit goes (Commit buttons) |
  | `Commit hunks…` | The hunks to commit, of every local change, those of the files selected kept at first (Hunk picker), then as `Commit…`. What the pick leaves out stays as it was, staged or not (Spec 006) |
  | `Reword…` | The message, from the commit's own without its `Change-Id`, which the reword keeps (Spec 003) |
  | `Rename…` | The name, from the branch's own |
  | `New branch…`, `New branch here…` | The name |
  | `Split into its own commit…` | The message of the first commit, which takes the files selected; the second keeps the commit's own |
  | `Split…` | The hunks of the first commit (Hunk picker), then its message; the second keeps the commit's own |
  | `Fold hunks into…` | The hunks to fold, of every local change or of the commit (Hunk picker), then where they go, as `Fold into…` does (Drag and drop) |
  | `Take the remote version…` | Whether to replace the branch's commits with its remote's: what only the local branch has goes |

  A message is of as many lines as it takes, confirmed by `Ctrl+Enter`; a name by `Enter`. An empty one is refused in the dialog, as a commit with no destination picked, and one left as it was runs nothing (`Nothing changed`), but a commit's message, which is new whatever it starts from.
- When it ends, the window reads the repository again, unless it was cancelled: what was open stays open, but for the cards of commits it rewrote, and a selection goes to the piece the cursor was on, alone, else to the one now in its place, else the nearest above. A branch the command created or renamed is selected instead.
- A push refused for a branch that has diverged hints to pick `Force push` in its menu.

## Drag and drop

A piece is dragged once the pointer moves 6 px with the left button down on it: the selection when the piece is in it, else that piece alone. What is dragged is dimmed, what it can land on is tinted green, and the pointer carries its name, then what letting it go there does; the piece under the pointer says that too, in place of what it holds, or on a line between two cards. Anywhere over the local changes pane stands for them all, and a file of a card for the card; the wheel scrolls the board, wherever the pointer is.

| Dragged | Let go on | Does | Runs |
| --- | --- | --- | --- |
| Local changes, local files | A card | `AMEND` | `loom fold zz\|<files> <commit>` |
| | A tag | `COMMIT HERE` | `Commit…`, the branch picked (Commands) |
| A card | Between two cards: the room between them, up to 8 px from each, and 6 px into either | `MOVE HERE` | `loom fold <commit> --above\|--below <commit>` |
| | The rest of a card it descends from | `AMEND` | `loom fold <commit> <commit>` |
| | A tag | `MOVE HERE` | `loom fold <commit> <branch>` |
| | The local changes | `UNCOMMIT` | `loom fold <commit> zz` |
| A file of a card | Another card | `MOVE` | `loom fold <file> <commit>` |
| | The local changes | `UNCOMMIT` | `loom fold <file> zz` |

- A card is offered no place it already has, nor the branch it is the tip of (Spec 007). To `Move…`, which folds into nothing, a card is the place over it in its upper half and under it in the rest.
- Several cards, a tag, and what can land nowhere are not dragged: the status bar says why (`fold: one commit at a time`, `fold: a branch cannot be folded`, `fold: nowhere to drop it`). Nor is the base, silently.
- Let go anywhere else, `Esc`, or another button pressed, runs nothing. While a drag goes on the keys do nothing else, and no menu opens; no drag starts while a command runs, nor under a dialog, the log or the hunk picker.
- `Fold into…` and `Move…` drag the selection without the button: the status bar asks where it goes (`Fold <what> into… — click where it goes, Esc to cancel`, `Move <what> — click where it goes, Esc to cancel`), and a click there drops it. `Fold into…` offers its folds only, `Move…` the places of its one commit only. `Fold hunks into…` sends the hunks its picker kept (`Fold <n> hunk(s) into…`), and ending it logs `Cancelled` under the read, as the picker's `Cancel` does. A click where it goes nowhere keeps the pick (`Click where it goes, or press Esc to cancel`); `Esc` or a right click ends it (`fold cancelled`, `move cancelled`). Meanwhile a click anywhere in the window answers the pick, and the wheel still scrolls the board. `Move…` refuses as `move: <why>`.

## Hunk picker

A command that takes hunks reads them first: the status bar says `<command line> — reading the hunks`, and the window is as busy as while a command runs (Commands). A commit of one hunk is not split: `split: one hunk only, nothing to split`; of none, `split: no hunks to pick`.

The picker then covers the window, headed by what it is for (`Split <short ID>: keep the hunks of the first commit`, `Commit: keep the hunks to commit`, `Fold: keep the hunks to fold`) and `<n> of <m> hunk(s) kept`. Its files are on the left, each with a box (checked when all its hunks are kept, a dash when some are), its status letters and its path, relative to the directory the window was started in. The hunks of the file shown are on the right, each headed by its first line with a box; a hunk left out is dimmed. A split keeps nothing at first, nor a fold of a commit's hunks; a commit or a fold of local changes the hunks of the local files selected (all of them for the header).

| Input | Effect |
| --- | --- |
| Click on a file | Shows its hunks |
| Click on a file's box, `Space` on the file shown | Keeps every hunk of the file, or none when all are kept |
| Click on a hunk, `Space` on its box, which `Tab` reaches | Keeps it, or leaves it out |
| `↑` / `↓` | Shows the previous / next file |
| `Keep all` / `Keep none` | Every hunk of every file |
| `Enter`, the confirm button | What the pick is for (`Split…` and `Commit…` ask the message next, `Fold` where the hunks go) |
| `Esc`, `Cancel` | Closes it, running nothing: `<command> cancelled` |

- A split keeps a hunk on each side: confirmed with none kept, or all, the picker stays open and says `Nothing kept for the first commit` or `Nothing left for the second commit`. A commit keeps at least one: `Nothing kept for the commit`; a fold too: `Nothing kept to fold`.
- The hunks are handed to the command by id, with a fingerprint of the diff they were read from (Spec 019): the command refuses a diff that changed since.
- The log holds the read under the command line `-p` alone, then the command that ran. The message asked after `Split…` or `Commit hunks…` dismissed ends it as `Cancel` would: `Cancelled` in the log, `<command> cancelled`.
- A commit whose read finds nothing, as when every local change is a conflict, opens no picker: `commit: no hunks to pick`.

## Paused operation

While an operation is paused (Start-up), the local changes pane lists the working files it leaves, as `loom status` lists them, under how many there are and where the operation stands. The board gives its room to the inspector, which shows the file selected against HEAD, conflict markers included. Its first file is selected as it opens and after each command.

| State (Spec 020) | Headline |
| --- | --- |
| Unmerged paths | `Conflicts — resolve them, stage each file, then continue.` |
| Neither a rebase nor a merge left | `No rebase is in progress — Continue wraps the operation up, Abort discards it.` |
| None, `AUTO_MERGE` present | `No conflicts left — review them, then continue.` |
| Otherwise | ``Stopped part-way — `loom trace` says why. Continue once it is fixed.`` |

| Input | Effect |
| --- | --- |
| Click on a file, `↑` / `↓` | Selects it |
| `Stage`, a double click on a file | `git add` of the file, a deletion too, then the file that followed it is selected: `staged <path>`. Refused once what is paused is not the operation shown, as continue is, or not at the step shown |
| `Continue` | `loom continue` |
| `Abort…` | `loom abort`, once a dialog confirms it |
| Right click on a file | Selects it and opens its menu: `Stage` · `Continue`, `Abort…` |

- `Stage`, `Abort…` and `Continue` are the buttons under the files, and the inspector's, as for any selection; greyed out while a command runs, `Stage` with no file selected too. Continue and abort refuse an operation other than the one shown (Spec 020). Every other command says `<command>: an operation is paused`.
- After each, the window reads the repository again: still paused, as on another conflict or a failed step, it shows the pause; otherwise the integration branch.
- Closing the window leaves the operation paused, for the next window, `loom tui`, or `loom continue` and `loom abort`.

## Status bar and log

The status bar says the command running and the step it is at, or what was refused since it started. Once it ends: its last success, with `(and <n> more in the log)` when it reported more, or its last warning, else `Done`; `Cancelled`; or the first line of its error, which a dialog headed by the command line shows whole, unless the log is open. A refused command says why there. Backticks of the CLI's messages are left out.

`Log`, at its end, opens the log over the window: each command run since the window opened, as `$ <command line>`, then each line it reported, a success marked `•`, a warning or an error `!`, the hints under them `›`. `Esc`, `Enter` or a click outside it closes it.

A repository that cannot be read is said in a dialog and the status bar, in place of how a command went, which the log still has; the window shows it as it was.
