# Spec 020: TUI

## Overview

`git loom tui` opens an interactive, full-screen view of the integration
branch: the branch-aware status tree on the left (the same structure as
`loom status`), and the diff of the item under the cursor on the right.
Rows can be opened to reveal the files a commit changed, one or more rows
can be selected, and common loom actions (commit, fold, split, branch, drop,
reword, move) run directly from the tree without leaving it: prompts are popups,
results go to a log and the status bar. After every action the tree reloads
to reflect the new state.

## Why a TUI?

The status graph already names every entity with a short ID, but acting on
it still means reading an ID, quitting the pager, and typing a command.
The TUI closes that loop: navigate to the thing you see, press one key, and
the underlying loom command runs with the right arguments filled in.

## CLI

```bash
git-loom tui
```

No arguments or flags. The global `--theme` and `--no-color` options apply.

## Layout

```
┌ Status ──────────────────────┐┌ Diff ─────────────────────────┐
│ ╭─ z0 [local changes]        ││ diff --git a/src/main.rs ...  │
│ │   a1 M  src/main.rs        ││ @@ -1,3 +1,4 @@               │
│ │                            ││ +new line                     │
│ │╭─ b0 [feature-a] ✓         ││ ...                           │
│▓│●▓▓c2▓▓▓Add▓parser▓(2▓files)││   ← cursor row: shaded bg     │
│ ├╯                           ││                               │
│ ●  9999999 (upstream) ...    ││                               │
└──────────────────────────────┘└───────────────────────────────┘
 Navigate: ↑/↓ | Close/open: ←/→ | Select: space | Commit: c/C | Fold: f/F | ...
```

Short IDs are displayed like in `loom status`, so the tree doubles as a
cheat-sheet for manual commands; commit rows omit the abbreviated hash,
which is only noise next to the short ID. A row that exists only on screen has
no short ID and shows an inverted `[CREATE COMMIT]` / `[CREATE BRANCH]` tag in
its place, so it never reads as an existing entity. The cursor row is highlighted with a
subtle background shade (`Theme::selection_bg`: slightly lighter than a
dark background, slightly darker than a light one) so the row's own colors
stay readable — the hunk selector uses the same highlight.

- **Left pane (Status)**: the tree. One row per entity: the
  `[local changes]` header, working files, branch names, commits, commit
  files, the upstream marker, and context commits. Pure graph connectors
  (`│`, `├╯`, ...) are structural rows the cursor skips.
- **Right pane (Diff)**: the diff of the row under the cursor (see
  [Diff Pane](#diff-pane)). Cached per row until the tree reloads.
- **Status bar**: available shortcuts, mode hints, or a transient notice.

## Tree Content and Open/Close

The tree mirrors `loom status -f`, with rows that open and close:

- **Commits are collapsed by default.** A collapsed commit with files shows
  a dim `(N files)` hint. Opening one reveals a row per changed file, with
  its `<commit-sid>:<index>` short ID.
- **Local changes start expanded**, listing every staged, unstaged, and
  untracked file.
- `→`/`l`/`Enter` opens, `←`/`h` closes. Pressing `←` on a child file row
  jumps to its parent and closes it.
- Expansion state is keyed by commit OID, so it survives reloads (a commit
  rewritten by an action gets a new OID and closes again — acceptable).

## Navigation

| Key | Effect |
|-----|--------|
| `↑`/`k`, `↓`/`j` | Move the cursor (skipping structural rows); tree pane |
| `Tab` | Switch focus between tree and diff pane |
| `Ctrl-←` / `Ctrl-→` | Narrow / widen the left pane (2% per press, clamped to 10–90%) |
| `↑`/`k`, `↓`/`j` (diff focused) | Scroll the diff |
| `PgUp`/`PgDn` | Scroll the diff by a page |
| Mouse click / wheel | Focus, move, scroll |
| `L` | Toggle the action log popup (see [Actions](#actions)) |
| `R` / `F5` | Reload the tree from the repo |
| `+` (or `=`) / `-` | Show one more / one fewer context commit before the base, reloading the tree; starts at `loom.statusContext` (Spec 001), floor 1. Inactive while picking a fold target, placing a commit, or moving one. |
| `q` / `Ctrl-C` | Quit |
| `Esc` | End a `C`, `F` or `S` pick, taking effect when its read lands → cancel fold, commit, move, rename, or new-branch mode → clear selection → quit (first that applies) |

## Selection

`Space` toggles selection of the current row and advances the cursor.
Selected rows show a `✓` marker. Actions use the selection when one exists,
otherwise the cursor row. Selection is keyed by row identity and cleared on
reload — losing it after an action is expected. Collapsing a row also drops
the selection of the rows it hides, so an off-screen selection never blocks
the next one.

A selection holds one class of row: the local-changes header, working files,
branch names, commits, or commit files. No loom command takes a
heterogeneous target list, so toggling in a row of another class is refused
with a status-bar notice, leaving the selection as it was; `Esc` clears it.
The header is its own class — it is `zz`, which already subsumes the files
under it. Homogeneity is all the selection enforces: a class an action
cannot use (commits for `c`) or more rows than it accepts (several branches
for `d`) is still the action's own error.

While a target is being picked (`c`, `C`, `f`), the rows the pending command
takes are marked `▸` in the same gutter, outranking `✓`: what the command
takes matters more than what is selected, and `Space` cannot change the
selection anyway. Rows the command names are marked in full; rows a source
only subsumes are marked dim — the files under a `zz` header, and, for `C`,
the `[local changes]` header and the staged files under it, since the index
it commits is named by no row and the header is drawn even closed. The mark is
what keeps the source visible once the cursor moves on to the destination;
the pane title names the same sources (`Commit <sources> → [dest]`,
`Fold <sources> into...`, a count when they do not fit), for the ones
scrolled off. Both go when the mode does.

## Actions

Every action runs the regular loom command on a worker thread while the TUI
stays up (`core::ui`, the TUI counterpart of agent mode: `msg` prompts and
messages are redirected instead of touching the terminal):

- **Prompts** (`msg::confirm/input/select/select_or_input/multi_select`)
  become modal popups: text field, single/multi-select list with `↑/↓`,
  `Space` to toggle, `Tab` to complete a suggestion, `Enter` to confirm,
  `Esc` to cancel. A validator failure re-asks with the reason shown; a
  cancelled prompt ends the command as `Cancelled` (status-bar notice, no
  error popup).
- **Confirmations** are a **menu** (`widgets/menu.rs`), the shape every
  question is meant to take: titled with the running command line, the
  question (without its `?`) as the first item and `Cancel` as the second,
  the cursor item drawn as a full-width bar, `N of M` in the bottom border,
  80 columns wide (narrower terminals shrink it). `↑/↓` move, `Enter` picks
  (`Cancel` answers no), `Esc` always leaves. An item may carry a shortcut
  letter, shown in a left gutter, and a help text, possibly several lines,
  shown in a box below the menu while it is highlighted; the detail lines of
  a `msg::confirm` prompt (all but the first) are the help of its item.
- **Editors** are the one exception: `git::run_git_interactive` (commit
  without `-m`, reword's amend) hands the terminal back to the user for the
  duration and the TUI redraws afterwards.
- **The hunk selector** (`C`, `F`, `S`) is not an action: it runs before one, in two
  halves. Reading the hunks is a `git` per changed file, so a worker does it
  while the loop keeps drawing a spinner. `Esc` ends the pick, but its worker
  is waited for rather than abandoned: it reads with `git`, and one outliving
  its pick would run beside whatever the freed keyboard starts next, over the
  same index. A read that fails logs its error and reports it, and drops the
  pick. Every way out of a pick leaves a line in that entry, so a `C` that
  staged nothing is told apart from one that said nothing. Only the selector
  needs a terminal, so only it runs on the TUI's own thread, as a nested
  shell on the live one (`Tick::TakeOver` from
  `poll_background` → `ShellApp::take_over` → `Shell::run_nested`). Unlike an
  editor, nothing is torn down and set up again — the alternate screen, raw
  mode and mouse capture stay as they are, so the two screens replace each
  other without a flicker through the console. Its file pane is titled with
  the action the pick is for, `COMMIT`, `FOLD` or `SPLIT`, styled like the tree's
  tags; the CLI's selector, which runs for one known command, keeps `Files`.
  What `C` keeps it stages at once, through the same
  `staging::apply_selections` every `-p` command uses, so the commit that
  follows needs nothing but the index; what `F` keeps waits for its target
  and stages nothing until then; what `S` keeps is handed to `split -p` by
  id. It is one command: the press opens the `loom add -p <files>` (or
  `loom fold -p <sources>`, `loom split -p <commit>`) log entry, which stays
  even when the pick keeps nothing, and both halves install `ui` and report
  there — the worker included, where `msg` would otherwise print onto the
  screen the loop is drawing.
- **Messages** (`✓`/`!`/`✗` lines, spinners) go to the **log**. Each entry
  starts with the CLI line equivalent to the action, written with the short
  IDs the tree shows (`loom fold a1 fb`), followed by the lines the command
  emitted. `L` toggles the log popup. The status bar animates a spinner with
  the command line while it runs.
- **Success** shows the command's last `✓` line in the status bar until the
  next key, suffixed `(+N more, L: log)` when the command emitted several
  (one per target of `drop <a> <b>`). **Failure** opens an error popup dismissed with `Enter`/`Esc`;
  the tree reloads afterwards either way.

While an action runs, tree keys are ignored (only `L` works); `q`/`Ctrl-C`
are keys of the popup while one is open, and of the branch-name field while
a name is being typed. A `C`, `F` or `S` read is the same, except that a key it has no
use for is answered with nothing at all: a notice would take the spinner's
place in the bar. `Esc` ends the pick and `q`/`Ctrl-C` end the session, both
taking effect when the read lands, since the pick waits for its worker either
way. A read that finishes under an open popup waits for that too: the selector
draws on the bare terminal, and a popup would still hold the keyboard once it
returned. The trace log gets one file per action, named
`loom tui: <command line>`; the pick's covers its read, the half that runs
off the loop.

| Key | Command | Arguments |
|-----|---------|-----------|
| `c` | `loom commit` | Two-step. The selection (or the cursor row) names what goes in: working files, or the `[local changes]` header for `zz`. It is always passed as file arguments, so the index decides nothing: a file staged outside the TUI is committed whole. Only `C`, which has just shown the index and written it, commits the index itself. Any other row, or an empty working tree, is an error notice. The tree is then rebuilt with the commit faked in at its destination, drawn as the relocation will leave it (stack, split ownership, fork at the base), every branch kept where it is drawn — one the commit fills stays among the empty ones until it runs; `↑`/`↓` move it through the destinations, integration line first (`-i`), then every woven branch top to bottom (`-b <branch>`). `Enter` commits, `Esc` cancels. The message is prompted as usual. A branch that does not exist yet is not a destination: `b` creates it first. While placing, action keys are inactive, the wheel moves the destination like `↑`/`↓`, and a click is ignored: the cursor never leaves the placeholder. |
| `C` | `loom add -p zz` then `loom commit` | `c` with the hunks picked first. The selector (Spec 007) always opens over every local change, whatever the cursor or selection: it rewrites the whole index, so showing one file would hide what else it changes — the cursor row only says where to go back on cancel. Confirming stages what it kept and unstages what it dropped, the tree reloads onto that index, and the destination step follows with no file arguments: the commit is the index. The placeholder counts the files the index holds and the pane shows `git diff --cached`. Cancelling the read with `Esc`, cancelling the selector, or keeping no hunk, ends there with a notice and an untouched index; cancelling the *placement* leaves the staging done, like a `loom add -p` you did not follow with a commit. An empty working tree is an error notice. |
| `f` | `loom fold` | Two-step: `f` captures the selection (or cursor row) as sources; `↑`/`↓` (and the wheel, or a click on one) then walk only the rows the sources can fold into, read off the tree in its order, and the tag drawn after the target's short ID says what the fold does there. Fold is one thing going into another, so it never moves commits to a branch. Working files or `zz` → any commit, `[AMEND]`. One commit → `zz` `[UNCOMMIT]`, a commit it descends from `[AMEND]` (the fixup rule, Spec 007). One commit file → `zz` `[UNCOMMIT]`, another commit `[MOVE]`. A source commit, or a commit file's own commit, is `[NOOP]`: it is where the pick starts, and `Enter` on it is a notice. A branch, several commits or commit files, empty local changes, or sources with nothing to fold into are an error notice. `←`/`→` are inactive, so a commit-file source stays in view. `Enter` folds, `Esc` cancels. |
| `F` | `loom fold -p` | `f` with the hunks picked first, in the selector `C` uses: on working files or `zz`, over every local change, as `C` opens it whatever the cursor or selection (the command is `fold -p zz`); on a commit, over its own diff. The target walk that follows is `f`'s, with the picked files marked `▸` (a commit's covered, dim) and the title `Fold hunks of <sources> into...`. Working-tree hunks → any commit, `[AMEND]`: nothing is staged until the target is confirmed, so cancelling anywhere leaves the index as it was, unlike `C`; the fold then stages the picked hunks and folds exactly those paths, as `fold -p` does after its own picker (`fold::run_picked`), and refuses if those paths' changes moved since the pick — a binary's or submodule's content included, stamped as the hunks are read since the listing shows it only as a label. Commit hunks → `zz` `[UNCOMMIT]` or a commit the source descends from `[MOVE]` (Spec 007), run as `loom fold -p <commit> <target> --hunks <id>... --hunks-from <fingerprint>` (Spec 019), so a listing that went stale refuses rather than moves the wrong lines. A picked binary file moves whole, as `fold -p` moves it. A branch, several commits, empty local changes, or sources with nothing to fold into are an error notice at the press, before any read; keeping no hunk ends with `fold cancelled`. |
| `m` | `loom fold --above`/`--below` | One commit: the selection, else the cursor row; any other row, or several commits, is an error notice. `↑`/`↓` (and the wheel) walk it through the places it can go, the tree rebuilt with it there, tagged `[MOVE]`, and the cursor on it. The places are the distinct trees drawn by `--above`/`--below` every other commit and by `fold <commit> <branch>` for every branch not ending at it, in tree order, one per tree, spelled `--above`/`--below` where both reach it: a branch is never what the walk shows, only how an empty branch, or one of a co-located group, is reached. The preview follows the ref rules of Spec 007, keeps every branch where it is drawn — one the move fills or empties changes group only once it runs — and skips the places the command refuses as already in place. It starts where the commit is, an `Enter` there a notice; a commit with nowhere else to go is an error notice. `Enter` moves, `Esc` cancels; `←`/`→`, action keys and a click are inactive. |
| `s` | `loom split` | Commit files — the selection, else the cursor's — are the first commit, passed as cwd-relative paths; the rest of their commit is the second. A commit row, with no commit file selected, is `S`. Rows of several commits, any other row, a commit of one file (`S` splits it), or every file of the commit are an error notice. The first commit's message is prompted in the editor, as usual. |
| `S` | `loom split -p` | `s` with the hunks picked first, in the selector `C` uses, titled `SPLIT`, over the whole diff of the one commit the cursor or selection is or belongs to, whatever files are selected — as `C` shows every local change. Run as `loom split -p <commit> --hunks <id>... --hunks-from <fingerprint>` (Spec 019), so a listing that went stale refuses. A commit read with fewer than two hunks, keeping no hunk (`split cancelled`), or keeping every hunk ends with a notice, without running the command. Refusals are `s`'s, at the press, minus the file counts. |
| `b` | `loom branch new` | The tree is rebuilt with the branch faked in at its future tip — the cursor commit or branch tip (passed as `-t`), else the base — so it is drawn where it will land (split ownership, stack, co-located group, or empty section), with its name as a text field on its row. In a co-located group the placeholder sits on top, since its name — which decides the final order — is not known yet. `Enter` creates it; `Esc` or an empty name cancels and the tree reverts. |
| `d` | `loom drop` | Selected working files, all at once (`loom drop <a> <b>`); else the cursor commit, branch, working file, or the `[local changes]` header (`loom drop zz`). Confirmation as usual. Only files go together: a selection of several other rows is an error notice. |
| `r` | `loom reword` | Cursor commit: opens the editor. Cursor branch: the name becomes a text field on its own row (`Enter` renames, `Esc` cancels, an empty or unchanged name does nothing), and the rename runs as `loom reword <branch> -m <new-name>`. |

Arguments are passed as full commit hashes, branch names, or loom short IDs
(for files), so they resolve through the same paths as manual commands.

### Conflicts

If an action pauses on conflicts (a `LoomState` exists after it returns),
a popup gives the standard guidance to run `loom continue` or `loom abort`
and dismissing it exits the TUI, repeating the guidance in the terminal —
every other command is blocked while paused, so keeping the TUI open would
be misleading. Starting `loom tui` while an operation is paused is blocked
by the global paused-state check, like other commands.

## Diff Pane

What the right pane shows per row kind:

| Row | Diff |
|-----|------|
| `[local changes]` | `git diff HEAD` (staged + unstaged) |
| Working file | `git diff HEAD -- <path>`; untracked files show their content as added lines (binary and oversized files degrade gracefully) |
| Branch name | `git diff <parent-of-oldest-owned>..<tip>` — everything the branch owns; "no commits of its own" when empty; a branch being named with `b` shows no diff |
| Commit | `git show --stat --patch <oid>` |
| Commit being placed with `c` | The working-tree changes it will hold, as their own rows show them |
| Commit being placed with `C` | The index it will commit (`git diff --cached`) |
| Commit file | `git show --format= <oid> -- <path>` |
| Upstream / context | Informational text / `git show` of the context commit |

Diff text is fetched without color and re-colored by line prefix using the
TUI theme, so it follows `--theme` like the rest of loom.

## Edge Cases

- **Not on an integration branch / no upstream**: fails with the same error
  as `loom status`.
- **Hidden branches** (`loom.hideBranchPattern`) are excluded, and short IDs
  are allocated before hiding, exactly like `loom status`.
- **Action fails**: the error is a popup; after Enter the tree reloads.
- **Terminal safety**: a panic hook restores the terminal before unwinding —
  only for a panic on the TUI thread; a crashing worker is reported as an
  error popup. Mouse capture is always released on exit.
